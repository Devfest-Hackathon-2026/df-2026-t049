# 01 — 产品定位与问题定义（v0.1）

## 一句话

ReliefRoute Arena 将**虚拟灾害下的物资分配和运输决策**转化为开放式 Bot 竞赛：不同开发者使用统一环境、统一 API 和可复现评分，持续比较并改进调度策略。

## 目标用户

- **初学者与学生**：通过无代码策略表单理解“优先照顾谁”和“运输效率”之间的冲突。
- **算法开发者**：针对同一批场景编写 Bot、观察失误、迭代优化。
- **教师／竞赛组织者（后续）**：基于统一的基线和场景布置教学或评测任务。

## 要解决的问题（假设，需验证）

- 真实物流调度的约束复杂，初学者不易获得**可运行、可解释、可竞争**的练习环境。
- 如果缺少统一规则与公开基线，不同优化策略难以进行公平比较。
- 纯静态算法题通常无法直观展现需求突然增加、道路封闭后的动态重排过程。

这些是**待验证的用户问题**，不是已完成调研或已被实测证实的结论。

## 产品机制

**输入**：同一套场景、物资需求、道路状态、车队条件和随机事件。  
**决策**：Bot 每回合指定从仓库派车前往哪些避难所及携带多少物资。  
**结果**：裁判验证行动、推进状态，计算需求满足、及时性、公平性和效率，并生成回放。  
**迭代**：开发者调整策略，进行多场景比较。

## 与现有策略游戏/路径展示的区别

1. 不是用户手动操作游戏，而是以统一协议运行**自主策略 Bot**。
2. 不只是单场成绩，而是对**多场固定环境**统计比较。
3. 保留可复现状态、日志与指标，使失败原因可分析。
4. 允许非程序员通过规则型 Bot 参与，让编程选手与规则选手共享同一评价机制。

## 与真实救援的关系

本产品使用**虚构地图和简化资源模型**。高分仅代表在模拟规则下表现较好，不代表可用于真实灾害指挥。后续若希望接近研究工具，应补充真实任务约束、有效数据、已有研究基线、领域专家评价与伦理风险审查。

## 黑客松适配

- 参赛类别：**医療・福祉**，可强调教育与开源开发者参与的价值。
- 核心 Google 技术：Cloud Run（模拟/裁判）、Firebase Hosting（前端），Firestore 可选。
- 可选：Google Maps 展示层、Gemini 自然语言规则设置或赛后解释。
- 评分关注的可展示事实：多次种子可复现、明显不同的策略分数、可解释的行动日志、稳定部署。

## 需要用户访谈验证的问题

- 学习者是否比传统最短路径可视化更容易理解多目标调度？
- 开发者是否真的愿意为排行榜改进算法？
- 哪项指标最能激励合理策略而不是刷分？
- 比赛回放是否能让参赛者定位自己的策略错误？
