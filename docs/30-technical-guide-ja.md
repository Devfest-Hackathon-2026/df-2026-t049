# エンジン・Bot・採点・リプレイの技術ガイド

現行実装の読み方をまとめた補足です。初期中国語設計書を削除せず、現在のコードで確認できる仕様と分けています。利用開始は [README](../README.md)、DB と結算は [時間別リーグ](23-hourly-league.md)を参照してください。

## 1. シナリオとターン順序

アリーナは 24 ターン、リーグは 48 ターンです。実際の時刻や交通を再現するモデルではありません。道路は正の整数移動時間を持つ無向グラフで、Bot が道路を追加したり経路を直接指定したりすることはできません。

1. 当該ターンの道路封鎖・渋滞・需要増加を適用します。
2. 既に出発した車両を一度進め、到着時の配送と帰還を処理します。
3. 現在の公開観測を Bot に渡します。未来の需要・イベント計画は含めません。
4. Bot の応答を検証し、合法な配車について在庫を差し引きます。
5. 観測、受理・拒否、配送、イベント、状態、移動コスト、状態ハッシュを記録します。

そのターンに新たに配車した車両が動き始めるのは次の移動処理です。新しい道路へ進むときに現在の通行状態から最短経路を求め、走行中の道路では記録された残り時間を進めます。経路がなければ blocked として待ちます。描画上の距離はこの計算に使用しません。

## 2. 共通の Bot 契約

`decide(request)` の request は `protocol_version`、`match_id`、`scenario_version`、`turn`、`total_turns`、`observation` を持ちます。observation には `depot`、`vehicles`、`roads`、`shelters`、発生済み `events` が含まれます。標準 Bot、パラメーター Bot、制限付きコード Bot に同じエンジンの裁定を適用します。

```json
{
  "protocol_version": "0.1",
  "turn": 0,
  "actions": [
    {"vehicle_id": "V1", "type": "dispatch", "target_shelter_id": "S1", "quantity": 5}
  ]
}
```

これは応答形式の例であり、V1 の状態、S1 への経路、在庫などが実際に適切でなければ拒否されます。`turn` は現在の request の値に合わせます。行動を指定しない車両は新規配車されません。既存の輸送が取り消されるわけではありません。

裁定は整数の正の数量、容量、倉庫在庫、車両の存在・idle 状態・倉庫位置、避難所、到達可能性、同じ車両への重複指示を確認します。不正な行動を得点に変換しません。外部 HTTPS Bot 呼出しは未実装であり、初期仕様の `/decide` サービスを起動する必要はありません。

## 3. パラメーター戦略

| キー | 有効値 | 意味 |
| --- | --- | --- |
| `priority_rule` | `urgency`, `nearest`, `fair` | 期限の余裕、近距離、低い充足率を考慮する優先順位 |
| `load_rule` | `full`, `half` | 積載上限。half は容量の半分を整数切捨て、最低 1 |
| `dispatch_rule` | `any`, `full_load` | 配送可能量で出発、または積載上限まで積める場合に出発 |

組合せは 3 × 2 × 2 = 12 通りです。[fair-strategy.json](../examples/fair-strategy.json) が設定例です。追加キーや古い設計の `road_rule` / `risk_level` は受理しません。配送中と同ターンの予約分を需要から差し引いて配車します。最低充足率優先でも総合点の最大化を保証するものではありません。

## 4. 採点式と再計算

`scoring_version=0.1`。各避難所 s について、発生済み需要を D_s、実配送を R_s、期限内配送を T_s、優先度を p_s とします。バッチの受領量は需要量を上限とし、まだ発生していない需要は除きます。

- C = Σ(p_s R_s) / Σ(p_s D_s)：優先度で重み付けした需要充足率。
- T = Σ(p_s T_s) / Σ(p_s D_s)：同じ需要を分母とする期限内配送率。
- F = min(R_s / D_s)：需要がある避難所のうち最も低い充足率。
- E = C × max(0, 1 − U/B)：移動コスト U とシナリオの `efficiency_budget` B による効率。
- 総合スコア = 60C + 20T + 15F + 5E。

U は全車両の実移動ターンの合計で、帰路や未完了配送中の移動も含みます。blocked の待機は含めません。内部は Fraction による有理数計算で、総合点は丸め前の値から算出し、出力を小数第6位に丸めます。試合終了時にまだ積載中の物資は配送量ではありません。リーグの順位ポイントはこの総合点の相対比較から別途更新します。

`python -m reliefroute --rescore outputs/match.json` は記録の最終需要バッチと各ターンの移動コストから計算し、保存済み score / summary を採点根拠にしません。全ターンが順序どおりそろう記録と対応する採点版が必要です。初期の採点版・移動コストを持たない記録や比較レポート全体は対象外です。状態ハッシュは外部提出を認証する署名ではありません。

## 5. JSON と視覚リプレイ

試合 JSON は seed、シナリオ版、採点版、summary、score、ターンごとの log を含みます。log は公開観測、行動裁定、実配送、イベント、状態スナップショット、movement_cost、state_hash を保持します。CLI または画面のダウンロードから保存できます。

フロントは記録を読み、再生・一時停止、速度変更、前後移動、リセット、タイムライン移動を行います。イベント表示は選択した時点のスナップショットから再構築し、巻戻し時に未来の封鎖等を残しません。画面の最終スコアは途中ターンの累積点ではありません。

`map-geometry.js` と `map-renderer.js` は道路曲線と車両位置の共通幾何を使います。都市・川沿い・山間の 3 環境 × A/B/C の九配置は表示だけの差です。リーグの配置は時間帯と実際の道路構成から安定して選び、Bot・得点・言語・再生位置で変えません。隣接する時間帯で同じ配置になる場合もあります。

線が交差しても道路接続が追加されたとは解釈しません。道路・車両・施設を選択して実 ID と詳細を確認します。密集箇所には重なりが残ることがあります。モバイルの詳細表示は地図内のスクロールであり、データや輸送ルールを変更しません。

## 6. トラブルシューティング

- `No module named reliefroute`：リポジトリルートに移動し、Python 3 の実行ファイルを確認します。
- ポートが使用中：既存プロセスを確認し、別の `--port` を指定します。
- DB が開けない：表示されるパスと書込権限を確認します。空 DB の初期化は Web または local_league.py を使います。
- Windows のストア別名が動かない：インストール済み Python の実行パスを使用します。JS の Python 呼出しは `PYTHON` 環境変数で実行ファイルを指定できます。
- テストの loopback / 一時 DB が実行環境に拒否される：その制限を確認します。テストを削除したり期待値を変えたりしません。
- 本番のリーグだけ 503：ストレージ設定・認証・競合を確認します。失敗時に一時 DB へ切り替えて保存成功と見せる実装ではありません。
