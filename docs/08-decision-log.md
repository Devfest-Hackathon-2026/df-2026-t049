## 立即讨论的 6 个问题

## 2026-11-05：CLI 首个开发切片（ADR-015）

- 开发前提：用户在本次开发会话确认已经到开发开始时间，并授权开始实现。未独立核验 Discord 公告。
- 记录/实施：Codex；范围为用户授权的命令行模拟器，以下规则作为 `0.1-cli` 实现基线，不代表完整赛事规则已最终批准。
- 选择：Python 标准库、固定无向道路图、1 仓库/3 避难所/3 车/1 物资、24 回合（0～23）。先建立可手算案例，再扩展事件与随机生成。
- Bot 仅决定调度目标与数量；引擎按最短耗时自动寻路。同耗时按完整节点路径字典序、再按道路 ID 序列选择；车辆按固定 ID 顺序处理。
- 每回合先推进旧车一次，再提供观察、校验并派车。新派出的车下一回合开始移动；到达避难所后下一回合开始返程；返仓当回合允许再派车。每车每回合最多消耗一个移动时间单位。
- 卸货按 `(due_turn, batch_id)` 顺序满足已出现的需求，截止回合到达计为准时。超额货物保留在车上，返仓时归还库存；禁止预先满足未来需求。
- 回合 23 结算后结束，不额外推进车辆；在途货物保留于状态但不计有效配送。
- 响应须携带当前 `turn`；严格拒绝未知字段、非整数数量（包括布尔值）、错误回合及每回合超过车辆数的动作列表。逐项按响应顺序验证库存，同车重复请求拒绝；无效动作不扣库存。
- 内置 Bot 异常按本回合 wait 并记录通用错误码；尚未开放不可信代码/HTTP Bot，也未实现超时隔离。
- 放弃的首步方案：先搭 Web/云 API、完整 20～30 节点随机图、数据库。理由是它们不帮助验证物流守恒和回合语义。
- 对评分的影响：记录每批次有效配送/准时配送及实际行驶车回合；不实现、不冻结评分权重，不输出总分。
- 基线结果：固定 seed 0，最近优先配送 60 单位，其中准时 50 单位；行驶 24 车回合，全部车辆最迟在回合 10 完成返仓。详见 `12-cli-fixture.md`。


## 2026-11-05：事件、双 Bot 与评分（ADR-016）

- 记录/实施：Codex；用户已授权继续下一步（突发事件、紧急度优先 Bot 和评分）。
- 采用文档中的 60/20/15/5 作为开发评分基线，`scoring_version=0.1`；并非正式赛季权重最终批准。相比 ADR-015，开始输出分项和总分。
- 原手算场景升版为 `0.2-fixture`，新增 `0.2-events`。使用相同 4 节点图并补两条绕行边；暂不扩展到 20～30 节点，便于定位事件与评分问题。
- 公开 seeds 为 11/22/33。使用局部 `random.Random(seed)` 在运行前生成全部事件，Bot 的随机数消耗和调用顺序不影响计划；生成器与规则变更必须升版。外部场景导入/校验仍不开放。
- 回合开始先应用事件，再推进旧车、观察、决策。道路区间为 `[turn, end_turn)`；结束时恢复基础状态。重叠封路只要仍有一个有效就保持关闭；重叠拥堵系数相乘后只向上取整一次。用有理数避免小数计算误差。路段耗时在车辆进入时锁定。
- 私有计划从状态中分离，Bot 仅收到当前道路状态及已发生事件；不暴露计划、未来新增需求或恢复时刻。事件记录以 started/ended 表示生效与解除，仍只有原定义的三类事件。
- 紧急度优先：对尚未被在途货物预留的需求，优先最小 `due_turn - current_turn - travel_turns`；再依避难所权重降序、距离和 ID 排序。两种 Bot 均只用公开观察并走同一裁判。
- 效率预算 B=72（3 车×24 回合），固定在场景版本内；U 为实际移动的车回合数，包含去程/返程及末回合在途移动，排除 idle/blocked 等待。库存不足等约束可能使满分不可达。
- 评分用精确有理数计算后输出六位小数；总分从未舍入分项计算。非法动作只记录拒绝，不额外扣分。无需求场景拒绝计分；无配送时所有分项及总分为 0。
- 重算从完整日志最后状态的已产生需求与每回合移动成本计算，不使用缓存 score 或 summary。仅接受支持的计分版本与完整回合记录；这不是日志防篡改/签名服务。
- `--compare` 将固定三 seed 的六位小数总分取算术均值，按均分降序（同分按 Bot 名）排列。无数据库或线上赛季。
- 验证：原手算配送时间、60 单位有效配送、50 准时配送和 24 车回合保持不变，首次得分为 95。公开事件场景的分项变化与局限见 `13-events-scoring.md`。


## 2026-11-05：可视化前端与本地 API（ADR-017）

- 用户授权为现有项目制作可视化前端；实施范围为仓库内本地运行版本，不发布外部网站。
- 采用无构建依赖的 HTML/CSS/JavaScript 与 SVG；路网坐标仅用于展示，绝不参与寻路/评分。新增虚构显示名称映射 S1/S2/S3，不引入资源或角色类型。
- 为连接现有引擎，提供 Python 标准库的 loopback 开发服务器及只读 GET `/api/match`、`/api/compare`。引擎、评分公式、Bot 协议及场景版本保持不变。生产 Cloud Run/Flask 服务仍按后续部署阶段实现。
- 页面一次获取完整比赛结果，再按回合回放；不是实时推进服务器比赛。总分始终标明为整场最终成绩，当前需求/事件/车辆随时间轴变化，避免把最终分数误解为实时分数。
- 运行参数只接受内置场景、两种内置 Bot 和 32 位有符号整数 seed；基础夹具只接受 seed 0。拒绝未知/重复参数。静态资源使用白名单，不暴露仓库文件。
- 比赛记录由浏览器直接导出原始 JSON，不在前端重新计算/改写评分；服务器不持久化用户数据、不执行上传代码。
- 选择深色控制台、浅绿色主操作与状态、橙色拥堵和红色封路，提供文字说明避免只依赖颜色；支持键盘时间轴与原生表单控件。
- 未选择 React/地图 SDK：当前固定小图与 24 帧回放不需要额外依赖，优先让用户直接运行与验证。后续可以在同一数据接口上替换前端实现。
- 验证：30 项自动测试通过，浏览器验证场景/Bot 切换、95 分基础夹具、六场对照、对照回放跳转、时间轴与封路显示。桌面宽屏和窄屏均进行视觉检查。

# ADR — 每小时持续联赛扩展（2026-11-09）

用户明确要求先实现每小时场景、自动比赛和排行榜，并最终支持托管代码 Bot、公开观战、系统语言适配。采用独立 UTC 小时场景，所有参赛 Bot 获得相同环境；48 回合、六避难所、五车辆，沿用既有三类事件与评分。原固定样例不修改。

先实现持久化联赛核心，采用冻结参赛名单和原子结算；新 Bot 下一小时参赛。积分为同场成对胜负积分，每轮最多 ±16，平局不变。仅保留最新轮详细回放，保存历史成绩与积分以支持审计。SQLite 只是单持久主机实现，不用于 Cloud Run 临时盘。用户代码执行必须独立隔离；无访问时的定时调度和云端持久化仍需实施。范围状态见 docs/23-hourly-league.md。
# ADR — 小规模云端联赛持久化

复用经过测试的 SQLite 联赛事务，并以私有 Cloud Storage 快照作为云端权威状态。每次写入使用 generation compare-and-swap；并发冲突重载重算。Cloud Run 的临时文件仅作工作副本，绝不当作持久化成功。此方案减少首版迁移成本，但每次请求读取整个快照，只适用于小规模试用；生产容量须测量，后续可迁移 Firestore。每小时执行使用私有 Cloud Run Job，由 Cloud Scheduler 调用，不公开结算端点。实际云资源尚未部署。
# ADR — 首版代码 Bot 使用受限决策语言

为了实现用户自己编写并托管决策，同时不执行任意用户源码，首版采用明确列举语法的 Python-shaped AST 解释器。支持变量、循环、条件、算术、观察读取及动作构造；禁用导入、属性、宿主调用、网络/文件、递归等，按回合计步并限制数值和输出规模。不使用 eval/exec，也不把它宣传为完整 Python 或通用隔离沙箱。代码部署后不可变，修改需创建新 Bot；服务器保存源码，后续每小时独立执行。任意 Python/JS 的独立容器执行不作为首版必要依赖，明确保留为后续扩展。具体协议与限制见 docs/24-code-bots.md。
